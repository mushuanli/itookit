# LLM 执行体调度器 - 综合设计方案

## 一、设计概述

### 1.1 系统定位

LLM 执行体调度器（LLM Agent Scheduler）是一个**本地优先的智能任务执行引擎**，核心职责：

1. **作为本地应用与 LLM 之间的桥梁**：管理上下文、控制成本、保障安全
2. **作为 LLM 能力的放大器**：通过工具、技能、子代理扩展 LLM 的行动边界
3. **作为可靠性的守护者**：错误恢复、反压验证、预算控制确保任务可靠完成

### 1.2 核心设计原则

| 原则 | 体现 |
|------|------|
| **Agent Loop 为核心** | 自主多轮循环是第一公民，编排器是可选的上层调度 |
| **上下文即稀缺资源** | 四层压缩、渐进式工具暴露、子代理隔离都是在管理 128K 的"注意力预算" |
| **失败是常态** | 五类错误各有恢复策略，工具异常回馈而非中断 |
| **信任需要验证** | 反压验证让 LLM 的"完成声明"可被验证 |
| **小积木大组合** | 执行器可被编排器任意组合，实现复杂工作流 |

### 1.3 设计参考

- **Claude Code**：四层上下文压缩、流式工具执行、反压验证
- **Anthropic Agent Guidelines**：Sub-agent 作为上下文防火墙
- **12-Factor Agents**：Context Engineering 理念
- **Kubernetes**：Controller Loop 模式、声明式配置
- **Erlang/OTP**：Let it crash + Supervisor 容错模型

### 3.1 AgentLoopExecutor - Agent 循环执行器

#### 3.1.1 职责

Agent 循环执行器是整个系统的**心脏**，实现自主多轮决策循环：

```
┌─────────────────────────────────────────────────────────────────┐
│                      AgentLoopExecutor                          │
│                                                                 │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐         │
│  │  Session    │───▶│   Loop      │───▶│   Result    │         │
│  │  (Input)    │    │   Engine    │    │   (Output)  │         │
│  └─────────────┘    └──────┬──────┘    └─────────────┘         │
│                            │                                    │
│         ┌──────────────────┼──────────────────┐                │
│         ▼                  ▼                  ▼                │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐         │
│  │ Context     │    │   Budget    │    │   Error     │         │
│  │ Manager     │    │  Controller │    │  Recovery   │         │
│  └─────────────┘    └─────────────┘    └─────────────┘         │
│         │                  │                  │                │
│         └──────────────────┼──────────────────┘                │
│                            ▼                                    │
│                     ┌─────────────┐                            │
│                     │ BackPressure│                            │
│                     │  Validator  │                            │
│                     └─────────────┘                            │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.1.2 循环不变式

每轮循环遵循以下不变式：

```
LOOP:
  1. [Budget Check]      检查六维预算，超限则退出
  2. [Context Compress]  评估上下文使用率，必要时压缩
  3. [Build Prompt]      动态构建系统提示词
  4. [Build Messages]    构建消息列表（含压缩摘要）
  5. [LLM Call]          调用 LLM（带错误恢复）
  6. [Parse Response]    解析响应，提取工具调用
  7. [Branch]
     ├─ [Has Tools]      执行工具 → 结果回馈 → GOTO LOOP
     └─ [No Tools]       反压验证 → 通过则退出，失败则注入错误 → GOTO LOOP
```

#### 3.1.3 状态模型

```

    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
    │  IDLE   │───▶│ RUNNING │───▶│COMPLETED│    │ PARTIAL │
    └─────────┘    └────┬────┘    └─────────┘    └─────────┘
                        │              ▲              ▲
                        │              │              │
                        ├──────────────┴──────────────┤
                        │                             │
                        │         ┌─────────┐         │
                        └────────▶│ FAILED  │─────────┘
                                  └─────────┘
                                       │
                                       ▼
```

#### 3.3.2 预算检查时机

```
每轮循环开始前:
  budget.checkOrThrow(session.usage)
    ├─ 任一维度 ≥ 80% → emit BudgetWarning
    └─ 任一维度 ≥ 100% → throw BudgetExhaustedError

每次 LLM 调用后:
  budget.updateUsage(response.usage, model.costs)
```

### 3.5 BackPressureValidator - 反压验证器

#### 3.5.1 设计理念

> "LLM 说完成了，真的完成了吗？"

反压验证在 LLM 给出最终回复**之前**插入验证关卡，将验证失败的信息注入消息历史，让 LLM 自动修正。

#### 3.5.2 验证规则类型

```

│                   BackPressure Rule Types                        │

│ Rule Type        │ Example                                      │
├──────────────────┼──────────────────────────────────────────────┤
│ TypeCheck        │ tsc --noEmit                                 │
│                  │ 触发：file_write 之后                        │
│                  │ 意义：确保类型安全                           │
```

### 3.6 SubAgentRouter - 子代理路由器

#### 3.6.1 设计理念

> "子代理是上下文防火墙"

主代理的上下文窗口是宝贵资源。当任务需要大量 I/O（搜索文件、读取多个模块、追踪调用链）时，这些中间结果会迅速填满上下文，将主代理推入"笨蛋区间"。

子代理解决方案：
- **独立上下文**：子代理有全新的、空白的上下文窗口
- **精确指令**：只传递一个明确的任务描述，不传递主代理的完整历史
- **摘要返回**：子代理完成后只返回精炼的结果摘要
- **成本优化**：子代理可使用更便宜/更快的模型

#### 3.6.2 工作流程

#### 3.6.3 适用场景

| 场景 | 为什么用子代理 |
|------|--------------|
| **代码定位** | 搜索可能返回大量结果，主代理只需要精炼的位置列表 |
| **代码分析** | 分析需要读取多个文件，主代理只需要结论 |
| **文档研究** | 研究需要浏览大量文档，主代理只需要摘要 |
| **依赖追踪** | 追踪调用链可能很深，主代理只需要关键路径 |
| **日志分析** | 日志可能很长，主代理只需要关键错误 |

### 3.7 ToolService - 工具服务

#### 3.7.1 工具注册模型

```
┌─────────────────────────────────────────────────────────────────┐
│                      Tool Registration                           │
│                                                                 │
│  ITool {                                                        │
│    name: string          // 唯一标识                            │
│    description: string   // LLM 可见的描述                      │
│    sideEffect: SideEffect  // None | Local | External           │
│    timeoutMs: number     // 执行超时                            │
│                                                                 │
│    getDefinition(): ToolDefinition   // JSON Schema for LLM     │
│    isAvailable(session): boolean     // 动态可用性检查          │
│    execute(args, session): Promise<string>  // 执行逻辑         │
│  }                                                              │
│                                                                 │
│  SideEffect:                                                    │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ None     │ 纯读操作，可安全并行，自动授权               │   │
│  │ Local    │ 本地副作用（文件写入），需串行，需确认       │   │
│  │ External │ 外部副作用（网络请求），需串行，需确认       │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.7.2 批量执行策略

```
┌─────────────────────────────────────────────────────────────────┐
│                  Batch Execution Strategy                        │
│                                                                 │
│  Input: [read_file, read_file, grep, write_file, shell_exec]   │
│                                                                 │
│  Step 1: Partition by SideEffect                                │
│  ┌─────────────────┐  ┌─────────────────┐                      │
│  │ Reads (None)    │  │ Writes (Local+) │                      │
│  │ ─────────────── │  │ ─────────────── │                      │
│  │ read_file       │  │ write_file      │                      │
│  │ read_file       │  │ shell_exec      │                      │
│  │ grep            │  │                 │                      │
│  └─────────────────┘  └─────────────────┘                      │
│                                                                 │
│  Step 2: Execute Reads in Parallel                              │
│  ┌─────────────────────────────────────┐                       │
│  │ Promise.allSettled([                │                       │
│  │   read_file(...),  ─┐               │                       │
│  │   read_file(...),   ├─ Concurrent   │                       │
│  │   grep(...)        ─┘               │                       │
│  │ ])                                  │                       │
│  └─────────────────────────────────────┘                       │
│                                                                 │
│  Step 3: Execute Writes Serially                                │
│  ┌─────────────────────────────────────┐                       │
│  │ await write_file(...)               │                       │
│  │ await shell_exec(...)               │                       │
│  └─────────────────────────────────────┘                       │
│                                                                 │
│  Step 4: Collect Results (Original Order)                       │
│  ┌─────────────────────────────────────┐                       │
│  │ [read_result, read_result, grep_result,                     │
│  │  write_result, shell_result]        │                       │
│  └─────────────────────────────────────┘                       │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.7.3 内置工具清单

| 工具 | SideEffect | 超时 | 核心能力 |
|------|-----------|------|---------|
| `file_read` | None | 10s | 行偏移/限制，带行号输出 |
| `file_write` | Local | 10s | 创建/覆盖/编辑模式，自动创建目录 |
| `shell_exec` | Local | 120s | 灾难命令拦截，输出截断，AbortSignal |
| `glob_search` | None | 30s | glob 模式匹配，自动忽略构建目录 |
| `grep_search` | None | 30s | 正则搜索，跳过二进制，路径:行号格式 |
| `load_skill` | None | 5s | 动态加载 Skill，注入工具和指令 |
| `delegate_task` | None | 120s | 委托子代理执行独立任务 |

```
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ Layer 2: CACHE_PRUNE (urgency ≥ 0.80)                   │   │
│  │                                                          │   │
│  │ Identify low-value messages:                             │   │
│  │ • assistant messages without tool_calls                  │   │
│  │ • assistant messages < 100 tokens                        │   │
│  │ • NOT in last 10 messages (safe zone)                    │   │
│  │                                                          │   │
│  │ Remove up to 30% of qualifying messages                  │   │
│  │ Savings: ~5,000-10,000 tokens                            │   │
│  └─────────────────────────────────────────────────────────┘   │
│                              │                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ Layer 3: LLM_SUMMARIZE (urgency ≥ 0.85)                 │   │
│  │                                                          │   │
│  │ Take oldest 60% of messages                              │   │
│  │ → Call summarizer model with preservation prompt:        │   │
│  │   "Preserve: file paths, decisions, errors, constraints" │   │
│  │ → Replace old messages with summary                      │   │
│  │                                                          │   │
│  │ Before: 40 messages (~80,000 tokens)                     │   │
│  │ After: 1 summary message (~2,000 tokens)                 │   │
│  │ Savings: ~78,000 tokens                                  │   │
│  │                                                          │   │
│  │ Fallback (if LLM fails): regex extraction                │   │
│  │ → Extract file paths, error messages, key decisions      │   │
│  └─────────────────────────────────────────────────────────┘   │
│                              │                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ Layer 4: SLIDING_WINDOW (urgency ≥ 0.95) [EMERGENCY]    │   │
│  │                                                          │   │
│  │ Keep only last 6 messages (~3 turns)                     │   │
│  │ Prepend minimal context note                             │   │
│  │                                                          │   │
│  │ WARNING: High information loss                           │   │
│  │ Only used when other layers fail to bring below 70%      │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

## 十、与 llm-kernel 的关系

### 10.1 定位对比

| 维度 | LLM Executor Scheduler（本设计） | llm-kernel |
|------|----------------------------------|-----------|
| **核心隐喻** | Agent Harness（给 LLM 装安全带） | Execution Engine（通用执行引擎） |
| **设计焦点** | Agent 循环的深度优化 | 执行器的通用编排 |
| **LLM 角色** | 核心，是"大脑" | 执行器之一，与 HTTP/Script 平级 |
| **上下文管理** | 四层压缩，核心能力 | 基本缺失 |
| **错误恢复** | 五类分级策略 | 简单重试 |
| **编排能力** | 来自 llm-kernel | 核心能力 |

### 10.2 融合策略

```
┌─────────────────────────────────────────────────────────────────┐
│                    Integration Strategy                          │
│                                                                 │
│  本设计 AgentLoopExecutor 可作为 llm-kernel 的新执行器类型：     │
│                                                                 │
│  llm-kernel ExecutorRegistry:                                   │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 'agent'     → AgentExecutor (llm-kernel 原有，单轮)      │   │
│  │ 'agentLoop' → AgentLoopExecutor (本设计，多轮循环)       │   │
```

## 十一、总结

### 11.1 设计亮点

| 特性 | 价值 |
|------|------|
| **四层上下文压缩** | 在 128K 限制内最大化有效信息密度 |
| **五类错误恢复** | 生产级可靠性，LLM API 限流、过载、截断都有应对策略 |
| **反压验证** | LLM 的"完成声明"可被验证，自动修正错误 |
| **子代理防火墙** | 大量 I/O 操作不污染主代理上下文 |
| **渐进式工具暴露** | 减少工具定义的 token 开销，提升 LLM 决策质量 |
| **读写分离并行** | 最大化工具执行效率 |
| **三层权限评估** | 平衡安全性与用户体验 |
| **六维预算控制** | 防止失控的成本和时间消耗 |
| **编排器组合** | 支持复杂多 Agent 工作流 |

### 11.2 适用场景

| 场景 | 适用度 | 说明 |
|------|-------|------|
| **Coding Agent** | ★★★★★ | 核心设计目标 |
| **文档处理** | ★★★★☆ | 工具集需扩展 |
| **数据分析** | ★★★★☆ | 可通过 Skill 扩展 |
| **多 Agent 协作** | ★★★★★ | 编排器 + 子代理支持 |
| **长时间运行任务** | ★★★★★ | 会话持久化 + 预算控制 |
| **交互式对话** | ★★★☆☆ | 更适合任务型而非闲聊 |

### 11.3 后续演进方向

| 方向 | 优先级 | 说明 |
|------|-------|------|
| **多模态支持** | 高 | 图片/文件附件，Computer Use |
| **Thinking 支持** | 高 | 流式输出思考过程 |
| **MCP 完整集成** | 中 | 标准化的工具协议桥接 |
| **Worker 隔离** | 中 | 浏览器环境下的线程隔离 |
| **分布式执行** | 低 | 跨机器的 Agent 编排 |
| **学习与适应** | 低 | 从历史会话中学习改进 |

### 11.4 设计原则检查清单

| 原则 | 遵循情况 |
|------|---------|
| **SRP** | ✅ 每个模块职责单一（ContextManager 只管上下文，BudgetController 只管预算） |
| **OCP** | ✅ 通过 SkillRegistry、OrchestratorRegistry 支持扩展而不修改核心代码 |
| **LSP** | ✅ 所有 ITool 实现可互换，所有 IOrchestrator 实现可互换 |
| **ISP** | ✅ 接口精简（ITool 只有 5 个必要成员） |
| **DIP** | ✅ AgentLoopExecutor 依赖 ILLMGateway 接口，Factory 是唯一组装点 |
| **DRY** | ✅ 公共逻辑提取（token 估算、路径解析、表达式求值） |
| **KISS** | ✅ 核心循环逻辑清晰，复杂性封装在各守护组件中 |
| **YAGNI** | ✅ 只实现已验证需要的功能，MCP 等列为扩展点 |
| **CoC** | ✅ 合理默认值（预算、权限、压缩阈值），开箱即用 |
| **LoD** | ✅ 模块间通过接口通信，不暴露内部实现 |
